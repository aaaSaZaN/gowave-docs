## Setup

- **Remnawave 3.4.5** (`remnawave/backend:3.4.5`) versus **GoWave** with the PostgreSQL pool, background subscription history and dashboard statistics optimizations.
- Docker, each panel limited to **2 CPU and 2 GiB**, each with its own **PostgreSQL 17 on 1 CPU** and identical settings. Remnawave also gets Valkey (0.5 CPU), which it requires.
- The same data, created through each panel's API: 1,000 users, 20 hosts, a profile and a squad.
- Load is generated by [k6](https://k6.io) 1.6.1: each iteration is one HTTP request. Responses are validated: an error, an empty subscription or HTML counts as a failure.
- Run order alternates and is shuffled; every run has a warmup. Each run lasts 20 seconds, two repetitions, tables show the median.
- Latency is server response time (k6 `timings.duration`); p99 is the median across runs.

## Memory and startup

- **Memory** (median across all runs, whole panel container including workers): GoWave about 51 MiB, Remnawave about 1,030 MiB.
- **Startup** until the first authenticated API response (median of 10 trials): GoWave 228 ms, Remnawave 4.8 s.

## Worth knowing

- **Dashboard stats at 32 clients and more (up to 13×)** comes from coalescing concurrent requests: while one computation runs in the database, the others wait for its result. Such a stampede on one endpoint is rare; the everyday difference shows with a single client: **2.9×**.
- **Writes with a single client are slower on GoWave** (156 versus 240 requests/s). Under more load GoWave pulls ahead: 1.3-1.7× at 8 to 128 clients. We are looking into the cause.
- **Nodes are not part of the test.** Node management, traffic collection, HWID and real VPN clients were not measured, only the panel API.
- **This is a single-machine check**, not a capacity study: runs are short and the hardware is a workstation. The numbers show the ratio, not absolute limits.
