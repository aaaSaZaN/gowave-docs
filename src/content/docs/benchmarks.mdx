## Условия

- **Remnawave 3.4.8** (`remnawave/backend:3.4.8`) против **GoWave** на коммите [`6d2c357`](https://github.com/aaaSaZaN/gowave/commit/6d2c35788b3b038627b5e86e6c6486caff0851c8).
- Прогон в [GitHub Actions](https://github.com/aaaSaZaN/gowave-bench/actions/runs/42302481269) на раннере с 4 vCPU (AMD EPYC 9V45) и 16 ГБ RAM. Логи, сырые результаты и [workflow](https://github.com/aaaSaZaN/gowave-bench/blob/main/.github/workflows/benchmark.yml) открыты, прогон можно повторить.
- Docker, у каждой панели лимит **2 CPU и 2 ГиБ**, свой **PostgreSQL 17 с 1 CPU** и одинаковыми настройками. У Remnawave дополнительно Valkey (0,5 CPU), без которого она не работает.
- Одинаковые данные, созданные через API каждой панели: 1000 пользователей, 20 хостов, профиль и сквад.
- Нагрузку даёт [k6](https://k6.io) 1.6.1: каждая итерация - один HTTP-запрос. Ответы проверяются: ошибка, пустая подписка или HTML считаются неуспешными.
- Порядок прогонов чередуется и перемешивается; перед каждым - прогрев. Каждый прогон длится 20 секунд, повторов три, в таблицах - медиана.
- Перед каждым прогоном в базе обеих панелей выполняются `CHECKPOINT` и `VACUUM ANALYZE`, чтобы предыдущий прогон не замедлял следующий.
- Задержка - время ответа сервера (`timings.duration` в k6), p99 - медиана по прогонам.

## Пропускная способность

Режим *concurrency*: заданное число клиентов отправляет запросы без пауз, следующий - сразу после ответа. Так видно, сколько запросов в секунду панель реально выдерживает.

## Память и запуск

- **Память** (медиана по всем прогонам, контейнер панели целиком, включая воркеры): GoWave - около 39 МиБ, Remnawave - около 1042 МиБ.
- **Запуск** до первого ответа API с авторизацией (медиана 10 попыток): GoWave - 166 мс, Remnawave - 4,3 с.

## Что важно знать

- **Статистика от 32 клиентов (до 6,4×)** - заслуга объединения одновременных запросов: пока одно вычисление идёт в базе, остальные ждут его результат. Такое «стадо» запросов к одному эндпоинту бывает редко; повседневную разницу лучше показывает один клиент - **2,6×**.
- **При записи от 32 клиентов GoWave упирается в свой PostgreSQL**, а не в приложение: база с лимитом 1 CPU троттлится в 18-23 % периодов, контейнер панели - нет.
- **Ноды в тесте не участвуют.** Не измерялись работа с нодами, сбор трафика, HWID и реальные VPN-клиенты - только API панели.
- **Это общая виртуальная машина GitHub Actions**, а не замер предельной мощности: активная панель, её база и k6 делят 4 ядра, прогоны короткие. Цифры показывают соотношение, а не абсолютные пределы.

## Откуда эти цифры

Тесты лежат в открытом репозитории [gowave-bench](https://github.com/aaaSaZaN/gowave-bench): сценарии k6, запуск обеих панелей в Docker, подготовка данных и построение графиков. Прогоны идут в [GitHub Actions](https://github.com/aaaSaZaN/gowave-bench/actions/workflows/benchmark.yml): workflow собирает GoWave из исходников, скачивает образ Remnawave и сравнивает их на одной виртуальной машине.

У каждого прогона открыты логи, характеристики машины и сырые результаты в артефактах. Цифры на этой странице взяты из [прогона 42302481269](https://github.com/aaaSaZaN/gowave-bench/actions/runs/42302481269). Чтобы проверить их, сделайте форк репозитория и запустите workflow **Benchmark** с профилем `full`.
